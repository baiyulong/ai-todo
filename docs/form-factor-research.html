形态选型调研 · 2026-10

AI 干完活主动推给你：
该做成 Web、桌面 App，还是原生 App？

目标很明确——AI 通过 MCP 把已完成的任务推进 Todo，并可靠地提醒到你，让你及时接手剩下的部分。所以真正的决策点不是"UI 长什么样"，而是两件被混在一起的事：AI 怎么连上任务库，以及通知怎么真的送到你手机和桌面。

推荐结论

用 响应式 Web + PWA 做唯一一套前端，桌面端靠"安装为应用"、手机端靠"添加到主屏幕"；不要单独做 Electron/Tauri 壳，不要先做原生 App。
但必须额外补两个非 UI 组件：本地 MCP Server 与 多通道可插拔通知层。

  • 一套代码覆盖三端：桌面浏览器、桌面安装的 PWA（独立窗口 + 通知中心）、手机主屏 PWA（角标 + 推送）。
  • 桌面壳的真正价值不是 UI，是打包：它能把「MCP Server + 本地库 + 系统通知」封成一个安装包。想要这个，用 Tauri（不打包 Chromium），不用 Electron。
  • 通知层才是成败关键：国内 Android 的 Web Push 走 FCM，不通；iOS 的 Web Push 走 Apple 通道，可用。所以通道必须能插拔，不能只有一条。
  • 自建 vs 现成：如果只想要"AI 完成后提醒"，Todoist / Taskade 已有官方 MCP + 推送，半天搞定；自建的真正价值在本地自持、与 AI 会话产物深度关联、通知通道可控。

二、推荐架构

两个进程、一份 SQLite、零同步逻辑。AI 写库与你看列表天然一致。
MCP 传输选型：v1 用 stdio（本地子进程，客户端一行 npx 配置，凭据走环境变量，日志走 stderr、stdout 严格留给协议）。等你要「任意 AI 客户端填个 URL 就能远程接入」时，再把同一个服务额外暴露成 Streamable HTTP——按 2026-07-28 规范它已是无状态（不再有 Mcp-Session-Id，改用 Mcp-Method / Mcp-Name 路由头 + _meta 携带协议版本），鉴权走 OAuth 2.1 Bearer。老的 HTTP+SSE 传输已在 2025-03-26 废弃，不要新建。

数据模型

-- 单一数据源
tasks(
  id, title, detail,
  status,      -- pending/acked/done
  severity,    -- info/need_human/blocker
  source_session, source_agent,
  idempotency_key UNIQUE, -- 防重复推送
  links, created_at, acked_at
)

暴露给 AI 的 MCP 工具

todo_add(title, detail,
  severity, notify,
  links, idempotency_key)

todo_list(status?, severity?)
todo_ack(id)   -- 我已接手
todo_update(id, ...)
todo_done(id)

三、通知通道：决定你到底收不收得到

这是整个方案里最容易被低估的一环。国内环境下，Web Push 只在 iOS 上靠得住。
通道消息落在哪国内可用要装 App成本实现成本备注
Windows 原生通知桌面右下角 Toast ●●●否0极低 本地守护进程直接发，不依赖任何推送网关
BarkiPhone 通知 ●●●iOS 端要0 / 可自建极低 HTTP 一行；App 内可开「重要提醒」穿透勿扰
飞书 / 钉钉 / 企微机器人群消息 ●●●已有0极低 WebHook URL，国内可达性最好，落点是你每天会看的 App
Server酱 Turbo微信服务号 ●●●否0（免费 5 条/天）极低 懒得装 App 时的兜底
iOS Web Push（VAPID）主屏 PWA 通知 ●●●否0中 走 Apple 通道；需 iOS 16.4+ 且必须「添加到主屏幕」；Safari 单条载荷上限 2KB
Android Web PushPWA 通知 ○○○否0中 依赖 FCM，国内 Google 服务不可达 → 不可靠；海外正常
邮件 SMTP邮箱 ●●●否近 0低 最终兜底，延迟高、不适合当主通道
国内 Android 的硬约束：Chrome 的 Web Push 走 FCM，而 FCM 依赖 Google 服务在国内不可达，因此 Android + 国内 + 纯 Web Push ≈ 收不到。要么走上面的 WebHook / Bark 通道，要么做原生 App 接厂商推送（小米/华为/OPPO/vivo/荣耀）——这也是「必须支持安卓且要求必达」时唯一该推翻 Web 优先结论的理由。
桌面端为什么要单独走原生通知：桌面 Chrome 的 PWA 推送同样依赖 FCM，且关掉所有窗口后可能停止投递（Edge 开启 Startup Boost 后才稳定）。本地 daemon 直接发系统 Toast，零延迟、零依赖、离线可用——桌面场景没有理由用 Web Push。

四、风险与对策

按「一定会踩」的顺序排，不按可能性排。
  1. 通知漏达

    手机没装 PWA、没授权限、通道挂了、你人在飞机上——任一环节断了就收不到，而"漏达"恰好毁掉这个工具的全部价值。

    对策：至少并行两条通道（WebHook 为主 + iOS Web Push 为辅）；daemon 侧保留 30 天未读列表，打开 App 必能看到，不依赖推送到达
  2. 通知噪音

    AI 每完成一个子步骤就推一条，一天几十条，很快全部静音——这是同类工具最常见的死法。

    对策：severity 分级，只有 need_human / blocker 才推送；同一会话聚合为一条；5 分钟冷却；每日摘要兜底
  3. 重复推送

    AI 工具调用失败重试、用户重跑会话，同一件事被推两遍。

    对策：idempotency_key = session_id + task_id 建唯一索引，重复写入直接返回已有记录
  4. 设备不在同一网络

    家里 WiFi 之外打开手机页面就是"无法连接"。

    对策：Tunnel / Tailscale 暴露（推荐，仍是本地数据）；或引入云端中继只同步推送与快照
  5. iOS 订阅失效

    系统重启后 service worker 的 push 监听可能不触发；浏览器还会定期轮换订阅对象。

    对策：监听 pushsubscriptionchange 重新订阅、服务端把 404/410 视为退订并清理、定期校验订阅存活
  6. 任务内容外泄

    任务标题里常有内网地址、代码片段、客户名。

    对策：数据留在本机 SQLite；外发内容只做脱敏摘要；载荷不含敏感正文（点开再拉详情）

五、落地路线

先跑通「AI 推 → 我被提醒 → 我在手机上处理」这条主链路，再谈形态美化。
  1. v0 · 闭环验证（≈1 天）

    本地 daemon（Node）+ SQLite + 最小 REST + 一屏 Web UI + MCP stdio 三个工具（add/list/ack）+ 一个 WebHook 通道（飞书机器人或 Bark）。目标是亲手感受一次：AI 干活完，手机真的弹了。

  2. v1 · 成产品（≈2–3 天）

    响应式 PWA（manifest + service worker + 角标）+ Windows 原生通知 + Tunnel 暴露 + 噪声控制（severity / 聚合 / 冷却 / 幂等）+ 任务详情与来源链接回溯。

  3. v2 · 按需扩张

    远程 Streamable HTTP MCP（任意客户端连 URL）+ iOS Web Push(VAPID) + 多设备同步 + 可选的 Tauri 打包（把 daemon + MCP Server 装成一个 Windows 应用）。

六、什么时候应该推翻这个结论

如果下面任一条命中，就不要按上面的路线走。

主力是安卓手机，且要求必达

国内 FCM 不通，纯 Web Push 行不通。此时要么补 WebHook/Bark，要么上原生 App 接厂商推送通道。

要多人 / 团队共享

这已经不是个人 todo 的问题。直接用 Todoist / Taskade / Plane 的官方 MCP，别自己造轮子。

必须离线 + 一键安装 + 数据自持

那就加 Tauri 壳，但要清楚它打包的是「daemon + MCP Server + 本地库」，UI 仍复用 Web 那套。

只是想被提醒一下

用现成的：Todoist / Taskade 有官方 MCP 和成熟推送，半天接入。自建的增量价值在「与 AI 会话、产物、来源深度关联」。

调研口径：MCP 传输规范依据 2026-07-28 版协议（stdio / Streamable HTTP，HTTP+SSE 已于 2025-03-26 废弃）；Web Push 能力依据 iOS 16.4+（Safari 18.4 Declarative Web Push、iOS 26 主屏站点默认独立窗口）与桌面 Chrome/Edge 行为；国内推送可用性依据 FCM 在中国大陆不可达的既有事实与国产通道现状。
